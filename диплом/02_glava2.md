# ГЛАВА 2. ВЫБОР И ОБОСНОВАНИЕ ИНСТРУМЕНТАЛЬНЫХ СРЕДСТВ РАЗРАБОТКИ

## 2.1 Обзор и сравнение кроссплатформенных GUI-фреймворков

Одним из первых ключевых решений при проектировании десктопного приложения является выбор GUI-фреймворка. Поскольку целевой платформой является Linux, а дополнительным преимуществом — возможность будущего портирования на другие платформы, к кандидатам предъявлялись следующие критерии:

- нативная или близкая к нативной производительность;
- декларативная или компонентная модель UI для продуктивной разработки;
- зрелая экосистема, документация и инструментарий;
- поддержка Material Design или иной современной системы дизайна;
- лицензия, допускающая применение в некоммерческих разработках.

Рассматривались следующие кандидаты.

### 2.1.1 Electron

Electron — фреймворк от GitHub для создания десктопных приложений на базе Chromium и Node.js. Позволяет использовать HTML, CSS и JavaScript для реализации пользовательского интерфейса.

**Преимущества:** богатая экосистема npm, знакомые веб-технологии, высокая скорость прототипирования.

**Недостатки:**
- Каждое Electron-приложение поставляет в себе полный браузерный движок Chromium (~150-200 МБ), что неприемлемо для специализированного инструмента;
- Высокое потребление оперативной памяти (типичное Electron-приложение потребляет 200-500 МБ RAM в фоне);
- Node.js и JavaScript не являются системными языками — интеграция с нативными библиотеками (например, чтение файлов pci.ids объёмом 3+ МБ построчно) требует дополнительных усилий;
- Производительность UI ограничена скоростью JavaScript-движка V8.

### 2.1.2 GTK4 / wxWidgets

GTK4 — низкоуровневый C-фреймворк, являющийся стандартным для GNOME. wxWidgets — кроссплатформенный C++-фреймворк с нативными виджетами.

**Преимущества:** минимальные зависимости, нативный внешний вид.

**Недостатки:**
- GTK4 ориентирован на C; C++-обёртки (gtkmm) менее зрелы;
- Оба фреймворка используют императивный подход к UI: каждый элемент создаётся и конфигурируется кодом, что существенно замедляет разработку;
- Отсутствует встроенная поддержка Material Design;
- Прототипирование UI значительно медленнее по сравнению с декларативными подходами.

### 2.1.3 Dear ImGui

Immediate Mode GUI — парадигма, при которой UI перерисовывается каждый кадр. Популярен в инструментарии разработчиков игр и отладчиков.

**Преимущества:** предельно простая интеграция, минимальные зависимости, высокая производительность для технических инструментов.

**Недостатки:**
- Не предназначен для сложных форм с состоянием: реализация биндингов данных требует значительного шаблонного кода;
- Внешний вид по умолчанию далёк от производственного уровня;
- Не предлагает компонентной модели для переиспользования.

### 2.1.4 Qt6 — выбор фреймворка

Qt6 — зрелый кроссплатформенный C++-фреймворк с декларативным языком QML для описания пользовательского интерфейса. Первоначально созданный Trolltech (ныне — The Qt Company), фреймворк используется в промышленности более 25 лет и является де-факто стандартом для Linux-десктопа в корпоративном и промышленном секторе.

**Преимущества Qt6:**
- Нативная производительность: Qt-приложения компилируются в нативный машинный код; нет интерпретируемого слоя;
- Декларативный QML: описание UI в стиле, близком к JSON/CSS, с мощной системой биндингов;
- Встроенный Material Design 2 (Qt Quick Controls 2);
- Зрелая интеграция с C++: макросы сигналов/слотов, свойства, Qt-модели данных;
- Qt Resource System: встраивание QML-файлов, JSON-пресетов и SVG-иконок прямо в исполняемый бинарник;
- Свободная лицензия LGPL 3.0 для некоммерческих и open-source проектов.

[РИСУНОК 2.1 — Сравнительная таблица GUI-фреймворков по ключевым критериям: производительность, декларативность UI, встроенный дизайн, зависимости, поддержка C++]

На основании проведённого анализа выбран фреймворк **Qt6** как наилучшим образом соответствующий совокупности критериев.

## 2.2 Фреймворк Qt6

### 2.2.1 Архитектура и модули

Qt6 структурирован в виде набора модулей; для данного проекта задействованы следующие:

| Модуль | Назначение |
|--------|-----------|
| `Qt::Core` | Базовые типы, потоки, файловая система, JSON-парсер |
| `Qt::Gui` | Абстракция от графической подсистемы платформы |
| `Qt::Quick` | Рантайм QML-движка и сцена для рендеринга UI |
| `Qt::QuickControls2` | Готовые UI-компоненты (TextField, ComboBox, ListView и др.) |
| `Qt::Qml` | Экспорт C++-типов в QML-движок |

### 2.2.2 Система сигналов и слотов

Сигналы и слоты — ключевой механизм реактивного взаимодействия в Qt. Сигнал — это событие, объявляемое в описании класса через макрос `signals:`. Слот — это обычный метод, который может быть подключён к одному или нескольким сигналам через `QObject::connect()`. При генерации сигнала все подключённые к нему слоты вызываются автоматически.

```cpp
// Объявление в заголовочном файле
class AppController : public QObject {
    Q_OBJECT
signals:
    void isModifiedChanged();
    void errorOccurred(const QString &message);
public slots:
    void saveReport();
};

// Подключение в конструкторе
connect(m_storage.get(), &Storage::errorOccurred,
        this,            &AppController::errorOccurred);
```

Данный механизм используется вместо устаревших макросов `SIGNAL()`/`SLOT()` — новый синтаксис обеспечивает проверку типов аргументов на этапе компиляции.

### 2.2.3 Свойства Q_PROPERTY и связывание с QML

Для экспорта данных C++-объекта в QML используется макрос `Q_PROPERTY`. Он объявляет именованное свойство с указанием геттера, сеттера и сигнала изменения:

```cpp
Q_PROPERTY(QString deviceTitle
           READ deviceTitle
           WRITE setDeviceTitle
           NOTIFY deviceTitleChanged)
```

В QML такое свойство становится доступным напрямую:

```qml
TextField {
    text: controller.deviceTitle
    onEditingFinished: controller.deviceTitle = text
}
```

Система биндингов QML автоматически подписывается на `deviceTitleChanged` и обновляет элемент, как только контроллер сгенерирует этот сигнал. Это полностью устраняет необходимость вручную обновлять UI при изменении данных.

### 2.2.4 Модели данных QAbstractListModel

Для передачи списочных данных (подсистемы, PCI-устройства, элементы чеклиста) из C++ в `ListView` в QML используется паттерн `QAbstractListModel`. Подкласс обязан реализовать три метода:

- `rowCount()` — количество элементов;
- `data(index, role)` — значение поля для заданного элемента и роли;
- `roleNames()` — отображение числового кода роли в строковое имя для QML.

```cpp
QHash<int, QByteArray> SubsystemModel::roleNames() const {
    return {
        {NameRole,       "name"},
        {DriverRole,     "driver"},
        {TestResultRole, "testResult"},
        {IsCompleteRole, "isComplete"},
    };
}
```

В QML элементы списка получают доступ к полям через имена ролей как к обычным свойствам:

```qml
ListView {
    model: controller.subsystemModel
    delegate: Text { text: model.name }
}
```

### 2.2.5 Qt Resource System

Qt Resource System позволяет встроить произвольные файлы (QML, JSON, SVG, изображения) в исполняемый бинарник на этапе компиляции. Обращение к ресурсам происходит через URI-схему `qrc:///`:

```cmake
qt_add_qml_module(ReportAssistant
    URI ReportAssistant
    VERSION 1.0
    QML_FILES src/ui/main.qml src/ui/WorkTab.qml ...
    RESOURCES resources/presets/subsystems.json
               resources/icons/disk.svg
)
```

Благодаря этому развёртывание приложения сводится к копированию одного исполняемого файла без зависимостей от внешних директорий с ресурсами.

## 2.3 Язык QML и декларативный подход

### 2.3.1 Основы QML

QML (Qt Modeling Language) — декларативный язык на основе JavaScript, разработанный специально для описания пользовательских интерфейсов. Каждый элемент UI представляется как объект с набором свойств, дочерними элементами и обработчиками сигналов:

```qml
Rectangle {
    width: 300; height: 44
    color: "#1E293B"

    Text {
        anchors.centerIn: parent
        text: "Системное тестирование"
        color: "white"
        font.pixelSize: 16
    }
}
```

Принципиальное отличие от императивного подхода: разработчик описывает **что** должно отображаться, а не **как** это нарисовать — рантайм QML сам вычисляет разностное обновление сцены.

### 2.3.2 Система биндингов и реактивность

Биндинг (привязка) в QML — это выражение, которое автоматически пересчитывается при изменении любого из задействованных свойств:

```qml
// title автоматически обновляется при изменении controller.currentFilePath
// или controller.isModified — без единой строки кода обработчика
text: (controller.currentFilePath || "Новый отчёт") +
      (controller.isModified ? " *" : "")
```

Такой механизм исключает класс ошибок «забыл обновить UI», характерный для ручного управления состоянием.

### 2.3.3 Разделение ответственности

В разрабатываемом приложении соблюдается строгое разделение: **вся бизнес-логика находится в C++**, QML выполняет только визуализацию и пробрасывает пользовательские события в C++. Это обеспечивает:
- тестируемость бизнес-логики без запуска GUI;
- ясную архитектурную границу между слоями;
- возможность заменить UI без изменения ядра.

Обновление данных в C++ из QML происходит только на событии `onEditingFinished` (завершение редактирования поля), но не `onTextChanged` (каждый нажатый символ) — это предотвращает петли обратной связи при программном обновлении поля из C++.

## 2.4 Язык программирования C++17

C++ выбран как основной язык реализации бизнес-логики по следующим причинам.

### 2.4.1 Интеграция с Qt

Qt6 изначально является C++-фреймворком. Весь инструментарий — MOC (Meta-Object Compiler), Q_PROPERTY, Q_INVOKABLE, шаблонные сигналы/слоты — рассчитан на C++. Реализация эквивалентного функционала на других языках через биндинги потребовала бы значительно больших усилий при меньшей надёжности.

### 2.4.2 Возможности C++17

Стандарт C++17, использованный в проекте, предоставляет ряд важных улучшений:

**`std::unique_ptr` и владение ресурсами.** RAII-умные указатели гарантируют освобождение ресурсов при выходе из области видимости и исключают утечки памяти без необходимости ручного `delete`:

```cpp
class AppController : public QObject {
    std::unique_ptr<ReportEngine>  m_engine;
    std::unique_ptr<ReportParser>  m_parser;
    std::unique_ptr<PresetManager> m_presetManager;
    std::unique_ptr<Storage>       m_storage;
};
```

**`std::optional<T>`.** Позволяет явно выразить «значение или его отсутствие» без использования нулевых указателей или специальных сигнальных значений.

**Структурированные привязки** (`auto [key, value] = pair`) — упрощают итерирование по контейнерам пар.

**`if constexpr`** — условная компиляция на этапе разбора шаблонов, полезная при работе с типами ролей модели.

### 2.4.3 Регулярные выражения (std::regex / QRegularExpression)

Разбор вывода `pci -vvv` и парсинг `.txt`-отчёта основаны на регулярных выражениях. В проекте применяется `QRegularExpression` — Qt-обёртка над PCRE2 с поддержкой именованных групп захвата:

```cpp
static const QRegularExpression reVendorDevice(
    R"(Vendor:\s+([0-9a-fA-F]{4})\s+Device:\s+([0-9a-fA-F]{4}))"
);
```

## 2.5 Система сборки CMake

### 2.5.1 Выбор CMake

CMake является официально поддерживаемой системой сборки для Qt6, начиная с Qt 6.0. Альтернативой служит qmake (`.pro`-файлы), однако он объявлен устаревшим и не получает новых функций. CMake обеспечивает:

- Стандартную интеграцию с IDE (Qt Creator, CLion, VS Code через cmake-tools);
- `find_package(Qt6 ...)` — автоматический поиск установленного Qt;
- Специализированные функции `qt_add_executable`, `qt_add_qml_module`, `qt_add_resources`.

### 2.5.2 Структура сборочного скрипта

```cmake
cmake_minimum_required(VERSION 3.16)
project(ReportAssistant VERSION 1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

find_package(Qt6 REQUIRED COMPONENTS Core Gui Quick QuickControls2 Qml)

qt_add_executable(ReportAssistant src/main.cpp ...)

qt_add_qml_module(ReportAssistant
    URI ReportAssistant
    VERSION 1.0
    QML_FILES src/ui/main.qml ...
)

target_link_libraries(ReportAssistant
    PRIVATE Qt6::Core Qt6::Gui Qt6::Quick Qt6::QuickControls2 Qt6::Qml)
```

Функция `qt_add_qml_module` автоматически запускает MOC для всех классов с макросом `Q_OBJECT`, а также RCC для встраивания QML и ресурсов. Разработчику не нужно вручную управлять этими утилитами.

## 2.6 Форматы хранения и обмена данными

### 2.6.1 JSON для пресетов и состояния сессии

JSON выбран для двух целей:

**Пресеты подсистем** (`resources/presets/subsystems.json`) — статический конфигурационный файл, встраиваемый в бинарник через Qt Resource System. Содержит 7 предустановленных подсистем с их иконками, списками стандартных драйверов, интерфейсов и типовых проверок. JSON читается однократно при запуске через встроенный `QJsonDocument`.

**Файл прогресса** (`<имя_отчёта>.progress.json`) — динамически создаваемый файл рядом с `.txt`-отчётом. Сохраняет полное состояние редактора: все поля ReportData, рабочие заметки и элементы чеклиста. JSON выбран вместо бинарного формата для удобочитаемости и возможности ручного восстановления данных.

Пример структуры файла прогресса:

```json
{
  "version": 1,
  "reportData": {
    "device": {
      "pageTitle": "Сервер ТАРГ-2-М",
      "model": "ТАРГ-2-М",
      "serialNumber": "2024-001"
    },
    "subsystems": [ ... ]
  },
  "workNotes": "Проверил USB 3.0 — работает\n",
  "workItems": [
    {"text": "Установить ОС", "done": true},
    {"text": "Проверить сеть", "done": false}
  ]
}
```

### 2.6.2 Собственный markup-формат (.txt)

Формат `.txt` с тегами (`@page`, `@group`, `@dl`, `@term`, `@ul` и др.) является внешним требованием: он потребляется Jenkins-пайплайном генерации PDF и не может быть изменён в рамках данного проекта. Задача приложения — гарантировать корректность генерируемых файлов.

Это разделение форматов принципиально: `.txt` содержит только формальный отчёт для внешней системы, тогда как `.progress.json` хранит всё рабочее состояние, включая данные, не входящие в отчёт (заметки, чеклист тестировщика).

### 2.6.3 Почему не YAML или XML

Рассматривалась возможность использования YAML для пресетов и прогресса. YAML обладает более компактным синтаксисом, но не поддерживается стандартной библиотекой Qt (потребовался бы сторонний парсер). XML поддерживается Qt через `QXmlStreamReader`, однако избыточен по синтаксису для простых структур данных. JSON в Qt6 не требует сторонних зависимостей и обеспечивает достаточный функционал.

## 2.7 Выводы по главе 2

Во второй главе обоснован выбор инструментальных средств разработки.

Проведён сравнительный анализ GUI-фреймворков: Electron отвергнут из-за избыточного потребления ресурсов, GTK4 и wxWidgets — из-за императивного подхода к UI и отсутствия встроенного Material Design, Dear ImGui — из-за несоответствия задачам форм с управляемым состоянием. Выбран **Qt6** как фреймворк с нативной производительностью, декларативным языком QML, встроенным Material Design и зрелой экосистемой.

Обоснованы ключевые механизмы Qt6: система сигналов/слотов для реактивного взаимодействия, `Q_PROPERTY` для экспорта данных в QML, `QAbstractListModel` для передачи списков, Qt Resource System для встраивания ресурсов в бинарник.

Выбран **C++17** как язык бизнес-логики — в силу нативной интеграции с Qt6 и возможностей RAII, `std::unique_ptr`, регулярных выражений. Обоснована система сборки **CMake** как официально поддерживаемая Qt6.

Определены форматы хранения данных: **JSON** для пресетов и файла прогресса — за счёт поддержки в стандартной библиотеке Qt без сторонних зависимостей; собственный **markup-формат .txt** — как внешнее требование пайплайна генерации PDF.
