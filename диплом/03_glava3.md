# ГЛАВА 3. ПРОЕКТИРОВАНИЕ И РЕАЛИЗАЦИЯ ПРОГРАММНОГО СРЕДСТВА

## 3.1 Общая архитектура системы

### 3.1.1 Выбор архитектурного паттерна

Для приложения с графическим интерфейсом выбор архитектурного паттерна определяет степень связности бизнес-логики и UI. Наиболее распространёнными паттернами в Qt-приложениях являются MVC (Model-View-Controller) и MVP (Model-View-Presenter).

В Qt6 с QML эти паттерны органично реализуются следующим образом:
- **Model** — структуры данных (`ReportData`) и Qt-модели (`SubsystemModel`, `PciDeviceModel`, `WorkItemModel`);
- **View** — QML-файлы, описывающие визуальное представление;
- **Presenter / Controller** — класс `AppController`, экспонирующий данные и операции в QML через `Q_PROPERTY` и `Q_INVOKABLE`.

Такое разделение позволяет изменить пользовательский интерфейс без затрагивания бизнес-логики и наоборот — модифицировать алгоритм генерации отчёта без переработки UI.

### 3.1.2 Диаграмма компонентов

На рисунке представлена компонентная диаграмма системы.

[РИСУНОК 3.1 — Компонентная диаграмма приложения: QML-слой (View) взаимодействует с AppController через Q_PROPERTY и Q_INVOKABLE; AppController делегирует задачи специализированным компонентам (ReportEngine, ReportParser, PciAnalyzer, PresetManager, Storage); данные хранятся в структурах ReportData и передаются через Qt-модели]

Система разделена на три горизонтальных уровня:

**Уровень представления (QML):** файлы `main.qml`, `WorkTab.qml`, `ReportTab.qml` и компоненты в `src/ui/components/`. Уровень не содержит бизнес-логики — только биндинги к свойствам `controller` и вызовы его методов.

**Уровень контроллера (C++):** класс `AppController` — единственная точка взаимодействия между QML и остальным кодом. Он агрегирует все компоненты, управляет состоянием приложения (текущий файл, флаг изменений) и маршрутизирует запросы QML к нужным сервисам.

**Уровень бизнес-логики и хранения (C++):** специализированные классы с единственной ответственностью — `ReportEngine`, `ReportParser`, `PciAnalyzer`, `PresetManager`, `Storage`.

### 3.1.3 Поток данных

Типичный сценарий взаимодействия при редактировании поля подсистемы:

1. Пользователь вводит текст в `TextField` в QML;
2. По сигналу `onEditingFinished` QML вызывает `controller.setSubsystemField(index, "driver", value)`;
3. `AppController` обновляет соответствующий элемент `SubsystemModel` и устанавливает флаг `isModified = true`;
4. `SubsystemModel` генерирует `dataChanged`, QML-`ListView` автоматически обновляет отображение;
5. При сохранении `AppController` передаёт текущий `ReportData` в `ReportEngine` для генерации `.txt` и в `Storage` для записи `.progress.json`.

## 3.2 Структуры данных (ReportData.h)

Все данные отчёта описываются в файле `ReportData.h` как простые C++-структуры (plain-old-data). Отсутствие наследования от `QObject` делает их легковесными и легко сериализуемыми.

### 3.2.1 CheckItem

Элемент чеклиста — отдельный шаг тестирования:

```cpp
struct CheckItem {
    QString text;
    bool    done = false;
};
```

### 3.2.2 SubsystemEntry

Полное описание одной аппаратной подсистемы:

```cpp
struct SubsystemEntry {
    QString name;         // Наименование (например, "Дисковые накопители")
    QString icon;         // Идентификатор иконки ("disk", "network", ...)
    QString controller;   // Строка контроллера из pci.ids
    QString interfaces;   // Список интерфейсов (текстовый)
    QString driver;       // Имя драйвера
    QString testResult;   // "pass" | "fail" | "partial"
    QString testNote;     // Примечание к результату
    QVector<CheckItem> checkItems;
    QString hintText;
    QString cautionText;
    QString warningText;
};
```

Разделение на три поля примечаний (`hintText`, `cautionText`, `warningText`) напрямую отражает три уровня разметки в отчёте: `@hint`, `@caution`, `@warning`.

### 3.2.3 OsInstallEntry

Отдельная структура для записи об установке ОС (всегда первая в отчёте):

```cpp
struct OsInstallEntry {
    QString testResult;
    QString testNote;
    QVector<CheckItem> checkItems;
    QString hintText;
    QString cautionText;
    QString warningText;
};
```

### 3.2.4 DeviceParams

Аппаратные параметры тестируемого устройства:

```cpp
struct DeviceParams {
    QString pageTitle;     // Строка заголовка (@page)
    QString model;         // Модель устройства
    QString serialNumber;  // Серийный номер
    QString motherboard;   // Системная плата
    QString bios;          // Версия BIOS/UEFI
    QString processor;     // Описание процессора
    QString chipset;       // Чипсет
    QString ram;           // Объём ОЗУ
};
```

### 3.2.5 ReportData — корневая структура

```cpp
struct ReportData {
    DeviceParams          device;
    OsInstallEntry        osInstall;
    QVector<SubsystemEntry> subsystems;
    QString               recommendations;
};
```

Именно `ReportData` передаётся как единый аргумент в `ReportEngine::generateReport()` и является результатом `ReportParser::parse()`. Все Qt-модели хранят ссылки на элементы этой структуры и обновляют её через методы `AppController`.

## 3.3 Модуль генерации отчётов (ReportEngine)

### 3.3.1 Назначение и интерфейс

`ReportEngine` преобразует заполненный объект `ReportData` в текстовый файл с разметкой. Его публичный интерфейс намеренно минимален:

```cpp
class ReportEngine {
public:
    QString generateReport(const ReportData &data) const;
};
```

Метод возвращает строку — полное содержимое `.txt`-файла. Запись на диск производит `Storage`, а не `ReportEngine`, что сохраняет принцип единственной ответственности.

### 3.3.2 Генерация раздела @group device

Первый раздел отчёта содержит две таблицы: параметры устройства и сводную таблицу подсистем.

```cpp
QString ReportEngine::generateDeviceGroup(const ReportData &data) const
{
    QString out;
    out += "@group device\n";

    // Таблица параметров устройства
    out += "@dl\n";
    out += QString("@term Модель @endterm %1\n").arg(data.device.model);
    out += QString("@term Серийный номер @endterm %1\n")
               .arg(data.device.serialNumber);
    // ... остальные поля ...
    out += "@enddl\n\n";

    // Сводная таблица подсистем (имя | контроллер | интерфейс | драйвер)
    out += "@dl\n";
    for (const auto &sub : data.subsystems) {
        QString name = sub.name;  // Сохраняем \n для отображения в таблице
        out += QString("@term %1 @endterm %2 | %3 | %4\n")
                   .arg(name, sub.controller, sub.interfaces, sub.driver);
    }
    out += "@enddl\n";
    out += "@endgroup\n\n";
    return out;
}
```

### 3.3.3 Генерация раздела @group tests

Наиболее сложный раздел — детальные результаты по каждой подсистеме. Для каждой подсистемы генерируется блок `@term..@endterm` с вложенным списком проверок и опциональными блоками примечаний:

```cpp
QString ReportEngine::generateTermBlock(const SubsystemEntry &sub) const
{
    QString nameFlat = sub.name;
    nameFlat.remove("\\n");  // В @term имя без переносов

    QString out;
    out += QString("@term %1\n").arg(nameFlat);
    out += QString("Результат: %1\n").arg(resultToString(sub.testResult));

    if (!sub.testNote.isEmpty())
        out += sub.testNote + "\n";

    // Список выполненных проверок
    if (!sub.checkItems.isEmpty()) {
        out += "@ul\n";
        for (const auto &item : sub.checkItems) {
            if (item.done)
                out += QString("@li %1\n").arg(item.text);
        }
        out += "@endul\n";
    }

    // Блоки примечаний
    if (!sub.hintText.isEmpty())
        out += QString("@hint %1 @endhint\n").arg(sub.hintText);
    if (!sub.cautionText.isEmpty())
        out += QString("@caution %1 @endcaution\n").arg(sub.cautionText);
    if (!sub.warningText.isEmpty())
        out += QString("@warning %1 @endwarning\n").arg(sub.warningText);

    out += "@endterm\n";
    return out;
}
```

Обратите внимание на строку `nameFlat.remove("\\n")` — это пример реализации правила: в `@term` имя подсистемы не должно содержать управляющего символа `\n`.

### 3.3.4 Гарантии корректности разметки

Поскольку генерация разметки централизована в `ReportEngine`, гарантии корректности достигаются структурно: каждый открывающий тег создаётся вместе с парным закрывающим в одном методе. Пользователь физически не может создать документ с незакрытым тегом через штатный интерфейс приложения.

## 3.4 Модуль разбора отчётов (ReportParser)

### 3.4.1 Задача и ограничения

`ReportParser` выполняет обратную задачу: преобразует существующий `.txt`-файл обратно в объект `ReportData`. Это необходимо при открытии ранее созданных отчётов для редактирования.

Разбор осложняется нерегулярностью формата: теги могут находиться как на отдельных строках, так и в одной строке с содержимым. Применяется подход конечного автомата со стеком состояний.

### 3.4.2 Конечный автомат парсера

Парсер обрабатывает файл построчно, переключаясь между состояниями:

```
IDLE
  → при встрече "@group device"  → IN_DEVICE
  → при встрече "@group report"  → IN_REPORT
  → при встрече "@group tests"   → IN_TESTS
  → при встрече "@group recomendations" → IN_RECOM

IN_TESTS
  → при встрече "@term ..."      → IN_TERM
  → при встрече "@endgroup"      → IDLE

IN_TERM
  → при встрече "@ul"            → IN_UL
  → при встрече "@hint ..."      → читает hint-текст
  → при встрече "@endterm"       → сохраняет SubsystemEntry → IN_TESTS

IN_UL
  → при встрече "@li ..."        → добавляет CheckItem
  → при встрече "@endul"         → IN_TERM
```

[РИСУНОК 3.3 — Диаграмма конечного автомата ReportParser: состояния (прямоугольники) и переходы по тегам (стрелки с условиями)]

### 3.4.3 Разбор строки @page

Строка заголовка имеет формат: `@page "pas" <Наименование> (заводской номер <Серийный номер>)`. Для её разбора применяется именованная группа захвата:

```cpp
static const QRegularExpression rePageLine(
    R"(@page\s+"pas"\s+(.+?)\s+\(заводской номер\s+(.+?)\))"
);

auto m = rePageLine.match(line);
if (m.hasMatch()) {
    data.device.pageTitle    = m.captured(1);
    data.device.serialNumber = m.captured(2);
}
```

### 3.4.4 Стратегия при отсутствии файла прогресса

Если рядом с `.txt`-файлом нет `.progress.json`, парсер восстанавливает данные только из разметки. При этом неизбежны потери: рабочие заметки, элементы чеклиста вкладки «Работа» и состояния флажков `done` у проверок не хранятся в `.txt`. Пользователь предупреждается об этом через сигнал `errorOccurred` с информационным сообщением.

Приоритет при открытии: сначала ищется `.progress.json` → при наличии восстанавливается полное состояние; при отсутствии → разбирается только `.txt`.

## 3.5 Модуль анализа PCI-устройств (PciAnalyzer)

### 3.5.1 Формат вывода pci -vvv в ЗОСРВ «Нейтрино»

Команда `pci -vvv` в ЗОСРВ «Нейтрино» выводит подробный дамп всех PCI-устройств. Каждое устройство описывается блоком строк вида:

```
Class = 0106h (Mass Storage)
Vendor = 8086h (Intel Corporation)
Device = 02d3h (Ice Lake-LP SATA Controller [AHCI mode])
```

Форматы немного отличаются в зависимости от версии прошивки, поэтому парсер использует регулярные выражения с необязательными группами захвата для учёта вариаций.

### 3.5.2 Загрузка базы pci.ids

База данных `pci.ids` содержит сопоставление числовых идентификаторов вендора и устройства их текстовым названиям. Файл структурирован иерархически:

```
8086  Intel Corporation
	02d3  Ice Lake-LP SATA Controller [AHCI mode]
	02f5  Ice Lake-LP Smart Sound Technology Audio Controller
```

Поскольку база содержит более 40 000 строк, она загружается однократно при первом обращении и кешируется в памяти в виде `QHash<uint32_t, VendorInfo>`, где ключ — vendor ID, а `VendorInfo` содержит имя вендора и `QHash<uint16_t, QString>` устройств.

Алгоритм поиска файла проверяет пути в порядке приоритета:
1. `<директория бинарника>/resources/pci.ids`
2. `/usr/share/misc/pci.ids`
3. `/usr/share/hwdata/pci.ids`
4. `~/.config/report-assistant/pci.ids`

[РИСУНОК 3.4 — Блок-схема алгоритма поиска файла pci.ids с резервными путями]

### 3.5.3 Разбор дампа PCI

```cpp
QVector<PciDevice> PciAnalyzer::parsePciDump(const QString &rawText) const
{
    QVector<PciDevice> result;
    PciDevice current;

    static const QRegularExpression reVendor(
        R"(Vendor\s*=\s*([0-9a-fA-F]{4})h(?:\s+\((.+?)\))?)"
    );
    static const QRegularExpression reDevice(
        R"(Device\s*=\s*([0-9a-fA-F]{4})h(?:\s+\((.+?)\))?)"
    );
    static const QRegularExpression reClass(
        R"(Class\s*=\s*[0-9a-fA-F]+h\s+\((.+?)\))"
    );

    for (const QString &line : rawText.split('\n')) {
        if (auto m = reVendor.match(line); m.hasMatch()) {
            current.vendorId   = m.captured(1).toUInt(nullptr, 16);
            current.vendorName = m.captured(2);
        } else if (auto m = reDevice.match(line); m.hasMatch()) {
            current.deviceId   = m.captured(1).toUInt(nullptr, 16);
            current.deviceName = m.captured(2);
        } else if (auto m = reClass.match(line); m.hasMatch()) {
            current.classStr = m.captured(1);
            // Если имена не пришли из дампа, ищем в базе pci.ids
            enrichFromDatabase(current);
            current.suggestedSubsystem = guessSubsystem(current.classStr);
            result.append(current);
            current = PciDevice{};
        }
    }
    return result;
}
```

### 3.5.4 Определение подсистемы по классу устройства

Функция `guessSubsystem()` сопоставляет строку класса PCI с одним из известных типов подсистем:

```cpp
QString PciAnalyzer::guessSubsystem(const QString &classStr) const
{
    const QString lower = classStr.toLower();
    if (lower.contains("mass storage") || lower.contains("sata") ||
        lower.contains("nvme"))               return "disk";
    if (lower.contains("network") ||
        lower.contains("ethernet"))           return "network";
    if (lower.contains("display") ||
        lower.contains("vga"))                return "monitor";
    if (lower.contains("usb"))                return "usb";
    if (lower.contains("audio") ||
        lower.contains("multimedia"))         return "audio";
    if (lower.contains("serial"))             return "serial";
    return {};  // Пустая строка — подсистема не определена
}
```

### 3.5.5 Формирование строки контроллера

После идентификации устройства формируется строка для вставки в поле «Контроллер» подсистемы:

```cpp
QString PciAnalyzer::buildControllerString(const PciDevice &dev) const
{
    // Формат: "Название устройства \n[**vendorid:deviceid**]"
    return QString("%1 \\n[**%2:%3**]")
        .arg(dev.deviceName.isEmpty() ? "Unknown Device" : dev.deviceName)
        .arg(QString::number(dev.vendorId, 16).rightJustified(4, '0'))
        .arg(QString::number(dev.deviceId, 16).rightJustified(4, '0'));
}
```

Обратите внимание: `\\n` — это строковый литерал «обратный слеш + n», записываемый в `.txt` как `\n` и интерпретируемый PDF-генератором как перенос строки.

## 3.7 Подсистема хранения данных (Storage)

### 3.7.1 Двухфайловая стратегия

Ключевое архитектурное решение хранилища — двухфайловая стратегия:

| Файл | Содержание | Потребитель |
|------|-----------|------------|
| `<имя>.txt` | Отчёт с разметкой | Jenkins PDF-генератор |
| `<имя>.progress.json` | Полное состояние редактора | Приложение при следующем открытии |

Два файла сохраняются атомарно: при каждом вызове `save()` обновляются оба. Это гарантирует согласованность: `.progress.json` всегда соответствует последнему сохранённому состоянию `.txt`.

### 3.7.2 Интерфейс Storage

```cpp
class Storage : public QObject {
    Q_OBJECT
public:
    bool save(const QString &filePath,
              const ReportData &data,
              const QString &workNotes,
              const QVector<WorkItem> &workItems);

    std::optional<LoadResult> load(const QString &filePath);

signals:
    void errorOccurred(const QString &message);
};
```

Метод `save()` возвращает `bool` — признак успеха. При ошибке (нет прав на запись, кончилось место) генерируется сигнал `errorOccurred`, который транслируется через `AppController` в QML и отображается пользователю в виде toast-уведомления.

### 3.7.3 Сериализация в JSON

Для сохранения `ReportData` в JSON применяется ручная сериализация через `QJsonObject`:

```cpp
QJsonObject Storage::serializeSubsystem(const SubsystemEntry &sub)
{
    QJsonObject obj;
    obj["name"]       = sub.name;
    obj["controller"] = sub.controller;
    obj["driver"]     = sub.driver;
    obj["testResult"] = sub.testResult;

    QJsonArray checks;
    for (const auto &item : sub.checkItems) {
        QJsonObject ci;
        ci["text"] = item.text;
        ci["done"] = item.done;
        checks.append(ci);
    }
    obj["checkItems"] = checks;
    return obj;
}
```

### 3.7.4 Fallback при загрузке

При открытии файла `load()` сначала ищет `<путь>.progress.json`. Если файл найден — восстанавливается полное состояние. Если нет — вызывается `ReportParser::parse()` и данные восстанавливаются частично из `.txt`. Частичное восстановление сопровождается предупреждением пользователю.

## 3.8 Qt-модели данных для QML

### 3.8.1 SubsystemModel

`SubsystemModel` — это `QAbstractListModel`, предоставляющий `ListView` в QML доступ к списку подсистем. Каждый элемент списка экспонирует следующие роли:

| Роль | Тип | Описание |
|------|-----|---------|
| `name` | QString | Наименование подсистемы |
| `controller` | QString | Строка контроллера |
| `interfaces` | QString | Интерфейсы (текст) |
| `driver` | QString | Драйвер |
| `testResult` | QString | "pass" / "fail" / "partial" |
| `testNote` | QString | Примечание к результату |
| `checkItems` | QStringList | Тексты проверок |
| `hintText` | QString | Текст hint-блока |
| `cautionText` | QString | Текст caution-блока |
| `warningText` | QString | Текст warning-блока |
| `icon` | QString | Идентификатор иконки |
| `isComplete` | bool | Все проверки выполнены? |

Вычисляемая роль `isComplete` позволяет боковой панели отображать индикатор прогресса для каждой подсистемы без дополнительной логики в QML.

Модель поддерживает операции CRUD:

```cpp
void SubsystemModel::addSubsystem(const SubsystemEntry &entry);
void SubsystemModel::removeSubsystem(int index);
void SubsystemModel::setField(int index, const QString &field,
                               const QVariant &value);
void SubsystemModel::addCheckItem(int index, const QString &text);
void SubsystemModel::removeCheckItem(int subsystemIndex, int itemIndex);
```

Каждая мутирующая операция обёрнута вызовами `beginInsertRows`/`endInsertRows` или `beginRemoveRows`/`endRemoveRows`, чтобы QML-`ListView` мог анимированно обновить отображение.

### 3.8.2 PciDeviceModel

`PciDeviceModel` отображает список PCI-устройств, полученных после разбора вывода `pci -vvv`. Он используется только в правом drawer «Анализатор PCI» и не участвует в формировании отчёта напрямую.

Особенность модели: вычисляемая роль `suggestedSubsystem` содержит имя подсистемы, предложенной автоматически на основе класса PCI-устройства. Пользователь может принять предложение или выбрать другую подсистему вручную из выпадающего списка.

### 3.8.3 WorkItemModel

Самая простая модель — список задач вкладки «Работа». Каждый элемент имеет текст и булевый флаг `done`. Модель не связана с `ReportData` — её содержимое сохраняется только в `.progress.json`.

[РИСУНОК 3.6 — Схема взаимодействия Qt-моделей с AppController и QML: SubsystemModel и WorkItemModel получают данные от AppController, предоставляют их ListView в QML, обратные изменения передаются через Q_INVOKABLE-методы AppController]

Workflow пользователя:

### 3.9.7 Ключевые UI-паттерны

**Обновление только на `onEditingFinished`.** Все поля ввода обновляют C++ только при завершении редактирования, не при каждом нажатии клавиши. Это предотвращает петлю обратной связи: C++ получает значение, обновляет свойство, генерирует сигнал, QML обновляет поле, снова генерируя событие изменения.

**Toast-уведомления об ошибках.** Ошибки операций (файловые I/O, некорректные данные) отображаются в виде временного уведомления в нижней части окна. Уведомление исчезает автоматически через 4 секунды. Реализовано через `Rectangle` с `Behavior on opacity` и `Timer`.

**Material Design.** Применяется тема `Material.Dark` с акцентным цветом `Material.Teal`. Все элементы управления из `QtQuick.Controls 2` автоматически следуют теме. Кастомные компоненты используют те же токены цвета.

```qml
import QtQuick.Controls.Material 2.15

ApplicationWindow {
    Material.theme: Material.Dark
    Material.accent: Material.Teal
}
```

## 3.10 Пример работы системы

### 3.10.1 Сценарий: создание отчёта с нуля

Рассмотрим полный сценарий работы специалиста по тестированию с использованием разработанного приложения.

**Шаг 1. Запуск и создание отчёта.** При запуске приложение открывается с пустым новым отчётом. Пользователь переходит на вкладку «Отчёт» → страница «Устройство» и заполняет основные параметры: наименование устройства, серийный номер, модель системной платы, версию BIOS, процессор, чипсет, объём ОЗУ.

[РИСУНОК 3.13 — Приложение в процессе заполнения параметров устройства: заполненные поля DeviceForm, статусная строка показывает «Новый отчёт *»]

**Шаг 2. Добавление подсистем.** Нажатием кнопки «+» в боковой панели открывается диалог выбора подсистем из пресетов. Пользователь выбирает нужные категории (например: «Дисковые накопители», «Сетевые адаптеры», «USB-контроллеры»). Каждая выбранная подсистема добавляется в боковую панель с иконкой и серым индикатором (не завершена).

**Шаг 3. Идентификация PCI-устройств.** Специалист копирует вывод `pci -vvv` из терминала ЗОСРВ и вставляет его в панель анализатора. После разбора в таблице отображается список устройств с предложенными категориями. Для каждого устройства он назначает соответствующую подсистему — строка контроллера автоматически вставляется в поле подсистемы.

**Шаг 4. Заполнение результатов тестирования.** Для каждой подсистемы специалист:
- отмечает выполненные проверки в чеклисте;
- устанавливает результат (успешно/неуспешно/частично);
- при необходимости добавляет примечания.

По мере заполнения индикаторы в боковой панели меняются с серых на зелёные.

**Шаг 5. Экспорт отчёта.** Через меню «Файл → Экспорт» пользователь выбирает путь сохранения. Приложение записывает два файла: `report.txt` с разметкой и `report.progress.json` с полным состоянием.

### 3.10.2 Фрагмент сгенерированного отчёта

Ниже приведён фрагмент генерируемого `.txt`-файла для подсистемы дисковых накопителей:

```
@group tests
@dl

@term Установка ОС
Результат: Выполнено успешно
@ul
@li Загрузка ОС с внутреннего накопителя
@li Загрузка менеджера загрузки
@endul
@endterm

@term Дисковые накопители
Результат: Выполнено успешно
@ul
@li Определение накопителей на чтение/запись
@li Проверка монтирования файловой системы ext4
@li Измерение скорости последовательного чтения
@endul
@hint Для повышения производительности рекомендуется использовать
файловую систему qnx6. @endhint
@endterm

@enddl
@endgroup
```

Сравнивая этот фрагмент с требованиями раздела 1.2.3, можно убедиться в корректности разметки: все теги закрыты, наименование подсистемы в `@term` не содержит `\n`, `@hint` имеет парный `@endhint`.

[РИСУНОК 3.14 — Сопоставление: поля редактора SubsystemDetail слева и соответствующий фрагмент сгенерированного .txt-файла справа]

### 3.10.3 Сохранение и восстановление сессии

После сохранения рядом с `report.txt` создаётся `report.progress.json`. При следующем открытии `report.txt` приложение автоматически обнаруживает файл прогресса и восстанавливает полное состояние: все поля, чеклисты с флажками, рабочие заметки. Специалист продолжает работу с той точки, где остановился.

## 3.11 Выводы по главе 3

В третьей главе описаны проектирование и реализация всех ключевых компонентов программного средства.

Выбран архитектурный паттерн MVP: `AppController` выполняет роль Presenter, QML-файлы — View, структуры `ReportData` и Qt-модели — Model. Такое разделение обеспечивает независимость бизнес-логики от пользовательского интерфейса.

Разработаны структуры данных (`ReportData`, `SubsystemEntry`, `OsInstallEntry`, `CheckItem`), полностью покрывающие все поля отчёта и обеспечивающие прямое отображение на markup-формат.

Реализован `ReportEngine`, гарантирующий структурную корректность генерируемых `.txt`-файлов: централизованная генерация исключает возможность создания отчёта с незакрытыми тегами. `ReportParser` реализует конечный автомат для разбора существующих отчётов с поддержкой fallback при отсутствии файла прогресса.

`PciAnalyzer` автоматизирует трудоёмкую процедуру идентификации PCI-устройств: разбирает вывод `pci -vvv`, обращается к базе `pci.ids` и формирует готовые строки контроллеров для вставки в отчёт.

Двухфайловая стратегия `Storage` обеспечивает раздельное хранение формального отчёта (`.txt` для Jenkins) и полного состояния сессии (`.progress.json` для редактора).

Пользовательский интерфейс на QML обеспечивает интуитивную навигацию и прямую работу со всеми элементами отчёта без изучения структуры разметки.
